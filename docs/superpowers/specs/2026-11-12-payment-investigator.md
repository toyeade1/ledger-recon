# Payment discrepancy investigator

User approved the proposed ledger-recon extension and asked to add the completed work to his resume on 2026-11-12. Build locally in an isolated branch. Preserve existing RL benchmark unchanged. This is a sandbox demonstrator, not a bank integration or a production deployment.

## Product and boundary
Upload a JSON bundle of invoice/transaction records and text/PDF remittance documents; inspect a queue of payment cases; investigate one payment; display proposed allocations with verifiable document quotations; explicitly approve an immutable proposal into a sandbox ledger; survive process restart without duplicate allocation. Include downloadable synthetic examples. No real bank credentials or employer data. Imported amounts use integer cents and one currency per matching case in v1. Reject cross-currency matches with an explicit unsupported explanation, not guessed FX. Existing RL environment retains its independent FX support.

## Architecture
Python package ledger_recon/investigator. SQLite owns invoices, transactions, documents, cases, proposals, approvals, allocations and append-only events. LangGraph handles persistent stages load -> retrieve -> extract -> validate -> finalize using SQLite checkpointer. Retrieval uses local embedded Qdrant; lexical + dense (Ollama embeddings when available, explicitly labelled lexical-only fallback) fusion by rank. Search IDs/amounts via authoritative SQL; semantic retrieval never defines accounting truth. Local Ollama JSON-schema-constrained proposals are untrusted: validate IDs/currency/amounts, document citations and quotations, and require current-document support for any adjustment. No paid cloud calls. Demo deterministic extraction mode is explicitly named 'rules' and never represented as model results. Local LLM integration must be exercised separately and results reported honestly.

Reuse existing ledger_recon.generate to make seeded plain matching fixtures; extend with separate synthetic evidence-discrepancy cases, never mutate existing benchmark/gold. Source case records are not retrieved from benchmark answer keys. Reuse architecture patterns from existing agent-runtime/doc-rag rather than introducing dependencies on their running services (gateway currently unhealthy).

## Validation details
Only positive integer monetary values in import (bool not accepted), valid ISO-like currency code, valid bounded IDs. Evidence adjustments initially support explicit credit notes linked to an invoice and amount; other unsupported shortfalls stay blocked. Overpayments, unknown customers, duplicate same-amount candidates, conflicting remittances, citation fabrication, missing docs and model errors must not produce actionable proposals. Customer identity and currency must match authoritative records. Validators must not accept arbitrary matching substrings as financial authorization. Quote must be an exact substring of the cited imported source; references/amounts must be structurally grounded in it. Account for partial payments and remaining balances on approval. SQLite foreign keys and transactions enforce all mutations. No tool/model/document may approve.

## Review refinements
Credits must be explicit objects `{credit_id, document_id, invoice_id, amount_cents}`. credit_id is parsed from an explicit credit-note identifier in the source, scoped to company/customer. Approval stores consumed credits with a unique credit_id constraint; a credit cannot be reused across payments. Amount/currency/customer/invoice identifiers must all agree with the source and SQL. Credit amount reduces invoice outstanding, not the incoming payment: sum allocations equals transaction cents; invoice paid allocations plus consumed credits never exceed invoice face value. A new proposal cannot reuse consumed credit evidence. Duplicated documents cannot evade credit identity uniqueness.

The store maintains a monotonically increasing evidence_revision. Any new invoice, transaction or document increments it; identical re-import does not. Proposal snapshots store this revision. Approval requires the current evidence revision and current proposal ID to match. A new conflicting document therefore invalidates older proposals until reinvestigation. Approvals also revalidate current invoice balances inside BEGIN IMMEDIATE. A single local company dataset per root; no multi-tenancy claim.
